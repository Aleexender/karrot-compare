# 버그율 비교: with-design vs no-design (2026-11-01, 로컬)

## 결론

두 앱을 실제로 띄우고 두 종류의 측정을 똑같이 실행했습니다.

1. **요구서 기반 측정 (24건)**: with-design의 요구서(`with-design/docs/01-post-create-requirements.md`)를 두 앱 공통 기준으로 삼아, 명시된 요구·추론한 엣지 케이스·완료 기준을 검사했습니다.
2. **일반 API 행동 측정 (27건)**: 요구서와 상관없이 어떤 API든 지켜야 할 기본 동작(요청 형식, HTTP 메서드, 데이터 보존, 응답 규약, 동시성)을 검사했습니다. 두 앱이 받은 프롬프트 차이의 영향을 받지 않는 측정입니다.

| 측정 | 구분 | 케이스 | with-design 실패 | no-design 실패 |
|---|---|---|---|---|
| 요구서 기반 | 명시된 요구 + 완료 기준 | 15 | 0 (0%) | 7 (46.7%) |
| 요구서 기반 | 추론한 엣지 케이스 | 9 | 0 (0%) | 3 (33.3%) |
| 일반 API 행동 | 요구서와 무관 | 27 | 1 (3.7%) | 4 (14.8%) |
| **전체** | | **51** | **1 (2.0%)** | **14 (27.5%)** |

- **요구서 기반**: no-design 실패 10건은 모두 요구서에 있는 기능이 없거나 다르게 동작하는 경우입니다. 같은 키 중복 방지, 네고·카테고리, 경로, 빈 내용 허용이 해당합니다. 이 측정에서는 두 앱 모두 5xx가 없었습니다.
- **일반 API 행동**: no-design은 긴 내용에서 **500이 2건** 났고, 201에 `Location` 헤더가 없습니다. with-design의 유일한 실패는 두 앱 공통인 데이터 손상 1건입니다(짝 없는 서로게이트 문자가 `?`로 저장됨).
- **완료 기준(동시 1만 건)**: 두 앱 모두 통과했습니다(2회씩 10,000/10,000). 다만 no-design은 처리 시간이 약 10배 길었습니다(3.3초 vs 30~35초).

## 비교의 전제 (공정성)

- no-design은 한 줄 프롬프트("POST로 게시글 올리는 API 하나 작성해줘", [원문](../no-design/docs/01-post-create-prompt.md))로 만들어졌습니다. 이 요구서를 받은 적이 없으므로, 이 측정은 "코드 품질"보다 **"요구사항을 얼마나 충족하는가"**를 잽니다. 설계 없이 시작하면 요구서와 얼마나 벌어지는지를 보는 것이 목적입니다.
- 두 앱의 API 계약이 달라서, 같은 논리 요청을 각 앱의 실제 형식으로 바꿔 보냈습니다(`measurement/functional.py`의 `App.post`).

| 항목 | with-design | no-design |
|---|---|---|
| 경로 | `POST /posts` | `POST /api/posts` (A6만 `/posts`로 따로 검사) |
| 작성자 | 헤더 `X-User-Id` | 본문 `sellerId` |
| 중복 방지 키 | 헤더 `Idempotency-Key` | 같은 헤더를 보내지만 앱이 무시 |
| 네고·카테고리 | 본문 `negotiable`, `categoryId` | 같은 필드를 보내지만 앱이 무시 |
| `location` | 보내지 않음 | 항상 `"서울"`을 보냄. no-design 필수 필드라 빼면 모든 요청이 400이 되어 비교가 무의미해짐 |

- 요구서 기반 측정의 판정 기준은 HTTP 상태 코드와 **DB 행 수 변화** 두 가지입니다. 응답만 보지 않고, 요청 전후 `items`/`posts` 행 수를 직접 셌습니다. 일반 API 행동 측정은 여기에 더해 저장된 값을 바이트 단위로 비교했습니다(기준은 "결과 상세 2" 절).
- 두 앱 모두 코드와 설정을 바꾸지 않고, 저장소에 있는 그대로 실행했습니다.

## 측정 과정

1. **환경**: MySQL 9.7.4(`karrot-mysql`, localhost:3307), Java 25, macOS(arm64). with-design은 :8081, no-design은 :8082에서 `./gradlew bootRun`으로 동시에 띄웠습니다.
2. **사전 확인**: with-design 테스트 스위트 `./gradlew clean test` → 92건 통과. no-design은 기본 `contextLoads` 테스트 1건뿐이라 따로 돌리지 않았습니다.
3. **데이터 준비**: with-design은 작성자 존재 확인을 하므로 users에 id 2(B9용)와 100001~101000(1만 건 부하용)을 넣었습니다. no-design은 users 테이블이 없어 준비가 필요 없습니다.
4. **요구서 기반 시나리오 23건**: `python3 functional.py`. 두 앱에 같은 순서로 실행합니다. 동시 클릭 케이스는 `threading.Barrier`로 요청을 동시에 출발시키고 10회 반복했습니다.
5. **완료 기준(동시 1만 건)**: `burst.sh` → `Burst.java`. 유저 1,000명 × 10건, 키는 모두 다르고, 가상 스레드 1만 개를 `CountDownLatch`로 동시에 출발시킵니다. 클라이언트 timeout은 연결 60초, 요청 120초입니다. 앱을 번갈아 2회씩 돌렸고, 클라이언트 임시 포트(TIME_WAIT)가 비도록 실행 사이에 90초씩 쉬었습니다. 시작 직전 TIME_WAIT는 42, 0, 0, 0개였습니다. 클라이언트 `ulimit -n`은 1,048,576입니다.
6. **일반 API 행동 27건**: 두 앱을 다시 띄운 뒤 `python3 general.py`. with-design에는 동시성 케이스용 users 100001~100100을 넣었습니다. 데이터 보존 케이스는 응답의 id로 DB에서 `HEX(컬럼)`을 읽어, 보낸 값의 UTF-8 바이트와 비교했습니다. 500이 난 케이스는 서버 로그로 원인을 확인했습니다.
7. **정리**: 측정마다 두 앱을 종료하고 측정 데이터를 지웠습니다. with-design에는 users id=1만 남겼고 items는 0행입니다. no-design은 측정 전부터 있던 posts 2행만 남겼습니다.

## 결과 상세 2: 일반 API 행동 (요구서와 무관, 27건)

요구서에 없는, 어떤 API든 지켜야 할 기본 행동을 따로 측정했습니다(`measurement/general.py`). 판정 기준은 세 가지이고, 하나라도 해당하면 실패입니다.
- **장애**: 5xx 응답 또는 연결 끊김
- **데이터 손상**: 2xx로 받아 놓고 DB에 보낸 값과 다른 값이 저장됨 (DB의 `HEX(컬럼)`을 보낸 UTF-8 바이트와 비교)
- **HTTP 규약 위반**: 잘못된 메서드에 405가 아님, 잘못된 형식에 4xx가 아님, 201에 `Location` 없음 등

"거부(4xx)"는 실패가 아닙니다. 길이 제한 같은 정책은 앱마다 다를 수 있어서, 값을 망가뜨리거나 서버가 죽지만 않으면 통과로 봤습니다.

| 구분 | 케이스 | with-design 실패 | no-design 실패 |
|---|---|---|---|
| 요청 형식 (G1~G8) | 8 | 0 | 0 |
| HTTP 메서드·경로 (G9~G12) | 4 | 0 | 0 |
| 데이터 보존 (G13~G21) | 9 | 1 | 3 |
| 응답 규약 (G22~G24) | 3 | 0 | 1 |
| 동시성·안정성 (G25~G27) | 3 | 0 | 0 |
| **합계** | **27** | **1 (3.7%)** | **4 (14.8%)** |

### 실패한 케이스

| # | 시나리오 | with-design | no-design | 판정 |
|---|---|---|---|---|
| G16 | 제목에 짝 없는 서로게이트(`"가\ud800나"`, JSON 이스케이프로는 유효) | ❌ 201, `가?나`로 저장 | ❌ 201, `가?나`로 저장 | 데이터 손상. 둘 다 거부하지 않고 받은 뒤 MySQL 드라이버가 `?`로 바꿔 저장함 |
| G18 | 내용 70,000자 (ASCII) | ✅ 400 (5,000자 제한) | ❌ **500** | 장애. 로그: `Data too long for column 'content'` (TEXT 최대 65,535바이트) |
| G19 | 내용 이모지 20,000자 (80KB) | ✅ 400 | ❌ **500** | 장애. 같은 원인 |
| G22 | 201 응답의 `Location` 헤더 | ✅ `/posts/{id}` | ❌ 없음 | 규약 위반 (RFC 9110: 201은 생성된 리소스 위치를 알려야 함). no-design은 조회 API도 없어서 가리킬 곳이 없음 |

### 통과한 케이스 (두 앱 공통)

- **요청 형식**: `text/plain` → 415, 본문 없음·`[]`·`null`·`{}`·잘못된 UTF-8·5,000단계 중첩 JSON → 400, 모르는 필드는 무시하고 201.
- **메서드·경로**: GET/PUT/DELETE → 405, 없는 하위 경로 → 404.
- **데이터 보존**: 이모지 제목, SQL 인젝션 형태 문자열, `<script>`, NUL 문자 모두 보낸 그대로 저장. 인젝션 뒤에도 테이블 유지. 가격 2^63 → 400.
- **동시성·안정성**: 같은 유저 50건 동시, 다른 유저 100명 동시 모두 전부 저장. 잘못된 요청 500건 직후 정상 요청 201.

### 참고 (실패로 세지 않음)

- **G21 가격 30억**: with-design은 201로 저장하고, no-design은 400으로 거부합니다. no-design의 가격 타입이 `Integer`라 약 21억 4,748만 원이 상한입니다. 값을 망가뜨리지 않고 거부하므로 기준상 통과지만, 중고차 같은 고가 물품은 올릴 수 없습니다.
- **G24 오류 응답 형식**: 둘 다 JSON입니다. with-design은 `application/problem+json`(RFC 9457), no-design은 Spring 기본 `application/json` 오류 본문입니다.

## 재현 방법

```bash
docker compose up -d
(cd with-design && ./gradlew bootRun) &   # :8081
(cd no-design   && ./gradlew bootRun) &   # :8082

# with-design 작성자 준비 (users id 1은 있다고 가정)
docker exec karrot-mysql mysql -ukarrot -pkarrot karrot_with_design -e "
  INSERT INTO users (id,nickname,created_at) VALUES (2,'bugrate-user-2',UTC_TIMESTAMP(6));
  INSERT INTO users (id,nickname,created_at)
    WITH RECURSIVE s(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM s WHERE n<1000)
    SELECT 100000+n, CONCAT('burst-',n), UTC_TIMESTAMP(6) FROM s;"

cd measurement
python3 functional.py   # 요구서 기반 23건, 결과는 functional.json
python3 general.py      # 일반 API 행동 27건, 결과는 general.json (users 100001~100100 필요)
./burst.sh              # 동시 1만 건 × 앱별 2회 (약 6분)
```
